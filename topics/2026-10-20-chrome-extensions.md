# 特集: Chrome 拡張機能をどう活かすか（2026-10-20）

職場の Web の業務システムを Chrome 拡張機能で効率化できるかを、流行り・事例・自動操作の可否・アイデア・セキュリティの順に調べたメモです。

- 調べ方: Web の検索と、検索に出たページの読み取り（2026-10-20）。調査の範囲は絞っています
- ラベル: **［事実］**＝この回に読んだページにそう書いてあった（ページの数字は数え直していない）。**［記憶］**＝前から知られていることで、この回は読み直していない。**［推測］**＝こちらの見立て

## 結論

- **自動操作は「作ってみてよい」側です。**ただし最初の一手は自作ではなく、既製の **Claude in Chrome** が職場の PC で使えるかを1回確かめることを勧めます。Claude の Team プランでは既定で有効で、手順の記録と定期実行もあり、API キーも要りません（2-1）
- **拡張機能だから通信が増えるわけではありません。**通信が起きるかは作り方で決まり、セキュリティが本題になるのは、画面の中身を社外へ送る作りにしたときだけです（4）

## 1. Chrome 拡張機能の開発の流行りと、注目の事例

### 流行り（3つ）

1. **拡張が「AI がブラウザを操作する入口」になった**
   - ［事実］Anthropic の **Claude in Chrome** は 2025-08 に Max の 1,000 人から始まり、2025-12-18 に有料プランすべて（Pro・Team・Enterprise）へ広がった。その時点で「一度やって見せた手順を覚えて繰り返す（Record a workflow）」「定期実行（Scheduled tasks）」「計画を承認したら最後まで任せる（Follow a plan）」が入っている（[リリースノート](https://support.claude.com/en/articles/12306336-claude-in-chrome-release-notes)）
   - ［事実］Claude Code からも同じ拡張を通してブラウザを操作できる。Chrome と **Edge** に対応。ログイン状態を共有するので、サインイン済みのサイトをそのまま触れる。ログイン画面と CAPTCHA では止まって人に頼む（[Claude Code のドキュメント](https://code.claude.com/docs/ja/chrome.md)）
   - ［事実、ただし孫引き］Google は Chrome 自体に Gemini の「Auto Browse」を入れ、OpenAI（Atlas）や Perplexity（Comet）は AI 搭載のブラウザそのものを出している（[frugaltesting の記事](https://www.frugaltesting.com/blog/agentic-browser-in-2026-how-chrome-comet-and-ai-browser-agents-are-changing-web-automation)。ソフトウェアテストの会社の記事で、比較の数字は確かめていない）
2. **ブラウザの中に AI のモデルが入り、拡張から無料で呼べるようになった**
   - ［事実］Chrome の内蔵 AI（Gemini Nano）の API のうち、翻訳・言語の判定・要約は Chrome 138 から正式。**汎用の Prompt API は拡張からなら Chrome 138 から使える**（Web ページからは 148）。文章を書く・書き直す・校正は、まだテスト中（[Chrome の一覧](https://developer.chrome.com/docs/ai/built-in-apis)）
   - ［推測］PC の中で完結して外へ送らないので、社内規程の面で通りやすい可能性がある。日本語の質と、どの性能の PC で動くかは測っていない
3. **AI に拡張を書かせる**
   - ［推測］拡張は HTML と JavaScript の小さな束で、ビルドの仕組みも要らないので、AI に丸ごと書かせやすい種類のソフトです。Teams のライブキャプション（字幕）を拡張で読み、Claude のアーティファクトへ送って使う、という拡張を AI に書かせて職場の PC で動かした例を、筆者は見ています

### 注目の事例（古いものも含む）

| 事例 | 何をするか | 優れている点（［推測］はこちらの見立て） |
|---|---|---|
| **Claude in Chrome**（2025〜） | AI がサイドパネルからタブを操作する | ［推測］「手順を一度見せれば覚える」で、RPA の「シナリオを作る」手間をなくそうとしている |
| **Scribe / Tango** | クリックを記録して、画面写真つきの手順書を自動で作る | ［記憶］業務マニュアル作りの手間をなくした。［推測］社内システムの手順書づくりにそのまま効く型 |
| **WalkMe などの「操作ガイド」系** | 他社製のシステムの画面の上に、吹き出しや入力の注意を重ねる | ［記憶］システム本体を直さずに、使い方の案内と入力チェックを足せる |

## 2. 拡張で社内システムを自動操作できるか。作ってみてよいか

### 結論

**技術的には「できる」。検討する価値もある。**決め手は技術ではなく、**職場の PC で何が許されているか**と、**画面が変わって動かなくなったときに誰が直すか**の2つです。

- ［記憶］拡張は、コンテンツスクリプト（content script）を使うと、画面の文字を読む・入力欄に値を入れる・ボタンを押す、といった操作ができる。昔からある基本の機能
- ［記憶］ただし拡張が作ったクリックには「人が押したものではない」というフラグ（isTrusted）が付き、これを見て弾く画面がまれにある。その場合は `chrome.debugger` で本物の操作として送れるが、画面上部に「デバッグ中」の通知バーが出る
- ［事実］Chrome をポリシーで管理している組織では、拡張を「許可したものだけ」「全部禁止」にできる。組織が配る拡張は、ID を固定して社内に置いて配れる（[記事](https://claudecodeguides.com/chrome-enterprise-blocked-extensions/)）。どんなポリシーが設定されているかは、`chrome://policy` を開けば見える

### やり方の一覧（作る前に選ぶもの）

| やり方 | できること | 課題 |
|---|---|---|
| **A. Claude in Chrome（既製）** | ［事実］Team プランでは**既定で有効**で、組織の管理者が切ることもできる。許すサイト・禁じるサイトの一覧を管理者が持てる（[管理者向けの説明](https://support.claude.com/en/articles/13065128-claude-in-chrome-admin-controls)）。手順の記録と定期実行がある。［事実］使うのは Anthropic の直接のプラン（Pro・Max・Team・Enterprise）で、API キーは要らない（Claude Code のドキュメント） | ［推測］管理者が切っているかもしれない。ストアからの導入を組織が禁じているかもしれない。1回ごとにモデルが画面を読むので遅く、利用枠も消費する。［事実、ただし孫引き］ページに埋め込まれた指示文で AI をだます「プロンプトインジェクション」は、AI のブラウザ操作の重い弱点とされている（frugaltesting の記事） |
| **B. 自作の拡張機能（AI なし、決まった手順を再生）** | ［推測］速い。利用枠を消費しない。結果が毎回同じ。画面が変わらず手順が決まっている作業ならこれで足りる | ［推測］画面の作りが変わると壊れる。直すのは作った人。自作の拡張機能を組織がどう見るかは組織しだい |
| **C. 自作の拡張機能 ＋ Claude のアーティファクト** | ［推測］拡張が画面を読む・書く手足、アーティファクトの中の Claude が頭。API を使わない。読む（要約・照合・判断）に強い | ［推測］アーティファクトを開いておく必要がある。両者の受け渡しを作る手間がある。「Claude の判断を受けて画面に書き戻す」向きは、まだ試した例を見ていない |
| **D. 組織が入れている RPA（Power Automate など）** | ［推測］組織が既に認めている道なら、社内規程の問題が無い | ［推測］入っているかは組織しだい。シナリオ作りが重い |
| **E. Chrome 内蔵 AI を使う自作の拡張機能** | ［事実］拡張からは Prompt API が使える（Chrome 138〜）。［推測］PC の外へ出ないので社内規程の面で通りやすい | ［推測］小さなモデルなので、判断の質は Claude より下。PC の性能しだいで動かない |

**勧める順（推測）: まず A を職場の PC で確かめ、駄目なら C を伸ばす。B は、A か C で「この手順は毎回同じ」と分かった作業だけを固める先。**B から始めると、毎回同じでない作業に当たったときに作り直しになるからです。

### 「作ってみてもいい」と言える条件（どれも推測）

- 同じ画面で、**同じ操作を週に何十回**もしている作業がある
- 手順が決まっていて、例外のときは人が見れば済む
- 失敗しても取り返せる（「送信」「承認」「削除」の最後の1押しは人が押す形にできる）
- 社内システムの画面が頻繁には変わらない

逆に、**最後の1押しまで任せる**のは勧めません。画面の読み違いや埋め込まれた指示文によって、取り消せない操作が実行されるおそれがあるからです。

## 3. 自動操作に限らず、できそうなこと

すべて［推測］のアイデアです。上ほど小さく、下ほど業務の形に踏み込みます。

**今の画面に足す（小さい効率化）**
1. **入力の下書き**: 申請や報告の画面で、メールや議事録から欄を埋めた下書きを出し、人は直して送るだけにする
2. **入力チェックを重ねる**: 送る前に「この組み合わせは過去に差し戻された」を画面の上に出す（WalkMe 型）
3. **転記をなくす**: システム A の画面の値を、システム B の入力欄へ流す（Excel を経由しない）
4. **画面の横で要約と翻訳**: 長い通知や英語の資料を、その場で読める形にする

**記録と知識（中くらい）**
5. **操作の記録から手順書を自動で作る**（Scribe 型）。異動や引き継ぎのたびにマニュアルを書かなくてよくなる
6. **「この画面で何をすればいいか」を、その画面の上で答える**: 社内規程や過去の問い合わせを Claude に渡しておき、画面の中身と合わせて答えさせる
7. **会議の字幕から、決まったことを社内システムへ**: Teams の字幕を読む拡張を伸ばし、会議中に出た「誰が・何を・いつまでに」をタスク管理の画面へ下書きする

**業務の形を変える（大きい）**
8. **誰がどの画面で何に時間を使っているかを見える化**: 拡張が操作の回数と時間だけを数え（中身は取らない）、自動化する作業の候補を数字で選ぶ。勘で選ばなくなる
9. **承認の流れを「確認だけ」に変える**: 書く人は下書きを AI に作らせ、承認する人は差分と根拠だけを見る。書く・読むの重さが入れ替わる
10. **社内システムを直す前の試し場**: 画面に足したい機能をまず拡張で重ねて使ってみて、効いたものだけを本体の改修として頼む。改修の当たり外れが減る

## 4. 拡張は通信が多い？ セキュリティはどう考えるか

ここは［記憶］と［推測］で書いています。この回に Web では確かめていません。

**拡張機能だから通信が増えるわけではありません。**通信は3段階に分けて考えられます。

1. **通信なし**: 拡張は、今開いている画面の文字を、その PC の中で読めます。ガイドの中身を拡張に同梱しておけば、「この画面ならこの吹き出し」は外へ一切送らずに出せます。画面の情報からガイドをポップアップさせる使い方は、この段で作れます
2. **社内だけ**: 社内システムを操作するときも、拡張は使う人のログインをそのまま使い、人が手で押すのと同じ通信をするだけです。新しい通信経路は増えません
3. **社外へ送る**: 画面の中身を Claude などへ送るときだけ、データが外に出ます。送り先が、組織が既に使ってよいと認めている AI なら、既存の利用許可の範囲として説明できる見込みです

**通信よりむしろ気にすべき点は2つです。**

- **権限が広いこと**: 「すべてのサイトを読む」権限の拡張は、社内のどの画面も読めてしまいます。読むサイトを社内システムだけに絞って書くのが基本です
- **ストアの拡張の乗っ取り**: 人気の拡張が買収や乗っ取りに遭い、更新で悪意のあるコードが配られた事件があります。自作して勝手に更新されない形にすれば、この心配は小さくなります

組織の IT 部門に申請するときは、「**どのサイトを読むか**」「**外へ送るか、送るならどこへか**」の2点を書いて出すのが要点です。
